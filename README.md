# Зобов'язання з дзвінка

Завантажуєте запис робочого дзвінка — отримуєте список того, про що **справді домовилися**. Не переказ розмови, а перелік зобов'язань: хто, що і до якого строку пообіцяв.

До кожного пункту додається дослівна цитата з таймкодом, і її можна **прослухати прямо в картці** — натиснули ▶ і чуєте той самий фрагмент запису.

---

## Навіщо це

Після дзвінка завжди лишається питання «то ми домовилися чи ні?». Звичайний переказ зустрічі тут не допомагає: він однаково сумлінно перекаже і те, що вирішили, і те, що просто обговорювали.

Різниця критична:

> — А давай заразом перепишемо авторизацію?
> — Хм. Ну дивись, у нас ще розсилка висить…
> — Та я просто до слова.

Переказ напише «обговорювали переписування авторизації». Цей застосунок скаже: **пропозиція, яку не прийняли** — і не покладе її до списку задач.

### Що застосунок уміє розрізняти

| Ситуація в розмові | Що потрапить у результат |
|---|---|
| «Візьму на себе» | Прийняте зобов'язання з власником |
| «А давай…» → тему звели | Запропоновано, але не прийнято. **Не задача** |
| Взяли задачу → потім скасували | Скасовано. **Не в активному списку** |
| «До п'ятниці… ні, давай понеділок» | Строк — **понеділок**, не п'ятниця |
| «Так, треба зробити» — але хто, не сказали | Задача є, **власника немає**. Нікого не призначаємо |
| «До кінця місяця чи наступного? Я плутаюся» | Обидва варіанти збережені, вибір **не робиться** |
| Питання прозвучало, відповіді немає | Відкрите питання, а не задача |

Головний принцип: **зберігається фінальний стан домовленості**, а не перша згадка. Якщо даних бракує — застосунок каже про це прямо, а не вигадує правдоподібне.

## Як це працює

```
запис → розпізнавання мовлення → розділення спікерів → мовна модель
      → перевірка цитат → список зобов'язань
```

1. **Готує аудіо.** ffmpeg приводить будь-який формат до однакового вигляду.
2. **Розпізнає мовлення.** faster-whisper перетворює звук на текст із таймкодами.
3. **Розділяє спікерів.** pyannote визначає, хто де говорить. Найдовший етап.
4. **Витягує домовленості.** Мовна модель отримує транскрипт і повертає структурований список зі статусами й цитатами.
5. **Перевіряє кожну цитату.** Ось це найважливіше — дивіться нижче.

### Захист від вигадок

Мовні моделі схильні вигадувати переконливі деталі. Тому останній крок робить **звичайний код, без жодного ШІ**.

Модель зобов'язана повертати цитати дослівно. Код бере кожну цитату й шукає її в транскрипті:

- знайшов точно → зараховує;
- не знайшов точно → шукає приблизно (пробачає інше закінчення чи пропущене слово, але не переказ);
- **не знайшов зовсім → пункт виключається з активного списку.**

Виключені пункти не зникають — вони показуються окремим блоком «Не підтверджено записом». Видно, що система їх побачила, але підтвердити не змогла.

Таймкоди теж не беруться зі слів моделі: код рахує їх із позиції знайденої цитати. Інакше кнопка «прослухати» програвала б не той фрагмент, і ніхто б цього не помітив.

### Що видно на екрані

Результат розкладений по блоках:

| | Блок |
|---|---|
| ✅ | Прийняті зобов'язання |
| ❓ | Відкриті питання |
| ⚠️ | Потрібно уточнити |
| 💭 | Запропоновано, але не прийнято |
| ❌ | Скасовано |
| 🚫 | Не підтверджено записом |

Останні три блоки потрібні не менше за перший: вони доводять, що систему **не обдурили** — вона ці випадки побачила й правильно відсортувала.

Унизу — панель із часом обробки по етапах і собівартістю прогону.

## Обмеження

Свідомо вузькі рамки, щоб зробити одну річ добре:

| Параметр | Значення |
|---|---|
| Мова запису | українська |
| Спікерів | 2 |
| Тривалість | до 3 хвилин |
| Одночасна мова | не обробляється |
| Формати | wav, mp3, m4a, ogg, opus, webm, mp4 |

Учасники мають **назвати себе на початку** — імена беруться з мовлення, а не вгадуються за голосом.

Обробка триває приблизно **втричі довше за сам запис**: хвилина аудіо — близько трьох хвилин роботи на звичайному процесорі. Основний час з'їдає розділення спікерів.

## Демо

Робочий стенд розгорнуто. Посилання, логін і пароль надсилаються окремо.

Пароль стоїть не заради «акаунтів» — сам застосунок жодної реєстрації не вимагає. Це замок на публічний стенд: без нього будь-хто, хто дізнається адресу, ганяв би розпізнавання коштом власника сервера.

## Встановлення на свій комп'ютер

### Windows, найпростіший шлях

```bat
git clone https://github.com/TimurPythonUser/meeting-commitments.git
cd meeting-commitments
install.bat
```

`install.bat` сам знайде Python, перевірить ffmpeg, створить віртуальне оточення й поставить залежності.

Далі відкрийте файл `.env` і впишіть два ключі (звідки їх узяти — написано в самому файлі). Після цього:

```bat
run.bat
```

Браузер відкриється сам, коли сервер буде готовий.

### Що потрібно мати заздалегідь

| | |
|---|---|
| **Python 3.11+** | https://www.python.org/downloads/ |
| **ffmpeg** | `winget install Gyan.FFmpeg`, потім перезапустити консоль |
| **Ключ DeepSeek** | https://platform.deepseek.com |
| **Токен Hugging Face** | https://huggingface.co/settings/tokens, тип Read |

Для токена Hugging Face додатково треба **прийняти умови двох моделей** — просто відкрити сторінки й натиснути згоду:
- https://huggingface.co/pyannote/speaker-diarization-community-1
- https://huggingface.co/pyannote/segmentation-3.0

Без цього розділення спікерів не запрацює.

### Через Docker (Windows, Linux, macOS)

```bash
cp .env.example .env     # і вписати ключі
docker compose up -d --build
```

Відкрити http://localhost:8000

Перше складання триває **10–20 хвилин**: качається torch і ваги моделей, образ виходить близько 5 ГБ. Зате моделі лежать усередині образу, і запуск потім миттєвий.

### Скільки це займає місця

| | |
|---|---|
| Залежності (torch та інше) | ~2 ГБ |
| Моделі розпізнавання й діаризації | ~1.5 ГБ |
| Оперативна пам'ять під час роботи | 3–4 ГБ |

## Розгортання на сервері

### Що потрібно від сервера

| | |
|---|---|
| Система | Linux x86_64 |
| Пам'ять | **від 8 ГБ** — на 4 ГБ моделі не піднімуться |
| Диск | від 15 ГБ |
| Процесор | від 2 ядер |
| Docker | будь-яка свіжа версія |

### Запуск

```bash
git clone https://github.com/TimurPythonUser/meeting-commitments.git
cd meeting-commitments
cp .env.example .env
```

У `.env`, окрім ключів, заповніть три рядки:

```ini
DOMAIN=ваш-домен.com
BASIC_AUTH_USER=
BASIC_AUTH_HASH=
SHUTDOWN_ON_DISCONNECT=0
```

Хеш пароля отримується однією командою (пароль вводиться двічі):

```bash
docker run --rm -it caddy:2 caddy hash-password
```

Запуск:

```bash
docker compose --profile public up -d --build
```

Усе. Caddy сам отримає сертифікат від Let's Encrypt і закриє стенд паролем.

### Якщо свого домену немає

Підійде **nip.io** — сервіс, що перетворює IP на ім'я без жодної реєстрації. Для адреси `203.0.113.10` домен буде `203-0-113-10.nip.io`. Сертифікат на таке ім'я видається нормально, а на голий IP — ні.

### Важливі дрібниці

`SHUTDOWN_ON_DISCONNECT=0` **обов'язково**. Локально застосунок гаситься, коли закрили вкладку — моделі займають гігабайти, тримати їх без діла немає сенсу. На сервері таке самовимкнення неприпустиме.

Токен Hugging Face потрібен і під час складання образу, і під час роботи. Ваги при цьому не качаються повторно — вони вже всередині, стоїть режим `HF_HUB_OFFLINE=1`.

## Тестовий набір

У репозиторії лежать три записи з наперед відомою відповіддю — `backend/tests/fixtures/`:

| Файл | Що перевіряє |
|---|---|
| `meeting_v1.wav` (2:39) | Усі складні випадки одразу: неприйнята пропозиція, виправлений строк, скасована задача, задача без власника, відносна дата |
| `meeting_v2.wav` (2:35) | Та сама розмова з **однією зміненою домовленістю**. Перевіряє, що застосунок справді обробляє вхід, а не віддає заготовку |
| `meeting_v3_ambiguous.wav` (1:08) | Розмова, де нічого не вирішили. Застосунок **зобов'язаний відмовитися** робити висновок |

Поруч — еталонні відповіді (`testset/expected_*.json`), написані **до першого запуску**, і часові вікна цитат (`testset/evidence_windows.json`): за ними перевіряється не лише склад списку, а й те, що таймкод показує на правильне місце запису.

Окремо є `testset/manual/` — п'ять коротших записів із різними голосами й темпом мовлення для перевірки руками.

Записи синтезовані навмисно: так точно відомі межі кожної репліки, і є з чим звіряти таймкоди. Сценарії лежать поруч у вигляді звичайного тексту, аудіо перегенеровується однією командою.

## Що під капотом

### З чого зібрано

| Шар | Інструмент |
|---|---|
| Сервер | Python 3.13, FastAPI, uvicorn |
| Розпізнавання мовлення | faster-whisper, модель `small` |
| Розділення спікерів | pyannote.audio, `speaker-diarization-community-1` |
| Витягування домовленостей | DeepSeek V4.1-Flash (`deepseek-flash`) |
| Обробка аудіо | ffmpeg |
| Інтерфейс | звичайні HTML, CSS і JavaScript — без збирачів і фреймворків |
| Розгортання | Docker, Caddy |

### Рішення, які варто пояснити

**Розпізнавання працює локально, не в хмарі.** Запис нікуди не надсилається — усе рахується на своєму процесорі. Змінна вартість розпізнавання нульова, але сервер під моделі коштує грошей, і в звіті вона рахується окремим рядком. Плата за це — швидкість: хмарне розпізнавання відпрацювало б за секунди.

**Мовна модель не рахує таймкоди.** Вона повертає текст цитати, а час бере код із транскрипту. Моделі не можна довіряти числа, які легко вигадати.

**Статус і власник — різні речі.** Задача, потрібність якої обидва визнали, вважається прийнятою, навіть якщо виконавця не назвали. Відсутній власник не перетворює задачу на «не прийнято».

**Дата запису береться з файла, а не з мовлення.** «Завтра» й «до четверга» немає від чого рахувати, якщо не знати дня розмови. Диктофони, Zoom і телефони пишуть дату в метадані файла — звідти вона й береться. Немає її там — відносний строк чесно лишається текстом із позначкою. Результат арифметики додатково перевіряється кодом: строк не може опинитися раніше за саму розмову.

**Черга на одну задачу.** Три хвилини аудіо завантажують процесор цілком, і друга паралельна задача нічого не пришвидшить — лише відбере ядра в першої.

### Перевикористаний компонент

`backend/app/vendor/transcriber.py` — ядро транскрипції з діаризацією, узяте з **власного телеграм-бота**, написаного раніше. У шапці файла перелічено, що взято без змін, що виправлено й що викинуто.

Правок дві: сегменти отримали пословні таймкоди, і з'явився прапорець, що їх вмикає. Без цього faster-whisper віддає шматки по 30 секунд, усередині яких встигають висловитися обидва співрозмовники — а тоді таймкод цитати їде на півхвилини й уся затія втрачає сенс.

Решта проєкту написана з нуля.

### Виміряно, не обіцяно

Реальний прогон на розгорнутому стенді (Hetzner CX33, 4 ядра), запис 68 секунд:

| Етап | Секунд |
|---|---|
| Підготовка аудіо | 0.2 |
| Розпізнавання | 18.2 |
| **Розділення спікерів** | **123.8** |
| Мовна модель | 76.6 |
| **Разом** | **219** |

**Вартість прогону — $0.0236**, за хвилину аудіо — **$0.0207**.

Токени того ж прогону: вхід 3190, вихід 19455. Вихід удесятеро більший, бо `deepseek-flash` міркує перед відповіддю, і ці міркування оплачуються за ціною виходу — саме вони й формують рахунок.

Припущення до цифр:
- ціни DeepSeek: $0.30 за 1M вхідних токенів, $1.20 за 1M вихідних, тариф peak (поза піком удвічі дешевше);
- розпізнавання локальне — змінна вартість $0;
- хостинг рахується **окремо** від вартості операції: Hetzner CX33 — $10.59/місяць за публічним прайсом;
- безкоштовні кредити провайдерів не враховуються: вони закінчуються, а прайс лишається.

## Що варто покращити далі

**Розділення спікерів — найповільніший етап** (майже дві третини часу). Хмарний сервіс розпізнавання з діаризацією відпрацював би за секунди й коштував би близько $0.004 за хвилину. Шар розпізнавання навмисно зроблено замінним — інший постачальник підключається заміною одного класу, решта конвеєра не змінюється.

**Витрати можна зменшити в рази.** Майже весь рахунок — це міркування моделі. Варто заміряти дешевшу модель на тому самому тестовому наборі й порівняти точність із вартістю.

**Довгі записи не підтримуються.** Понад три хвилини транскрипт перестане вміщатися зручно, і знадобиться розбиття на частини з окремим зшиванням домовленостей.

**Результати живуть у пам'яті процесу.** Перезапуск сервера їх стирає. Для демонстрації цього достатньо, для роботи потрібне сховище.
